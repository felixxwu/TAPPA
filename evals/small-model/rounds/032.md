### THE ROUND'S REAL FINDING: T013 is unwinnable-clean, and that is my authoring error

`test_menu_flow` reddens in six places. I checked whether that is the probe's fault, and it is not:

```gdscript
# Committing the focused car in the car park is what actually begins the run.
hq._on_start_pressed()
assert_true(ChallengeSession.is_active(), "committing the car park begins a ChallengeSession run")
```

The test asserts the commit begins the run **immediately and synchronously**. **Any** confirmation gating that
commit makes it false. That is exactly §2.5's cause — "an EXISTING test pins a product choice that a live bank task
exists to change, so no correct implementation can reach green" — and §2.5 says finding these is **my** job,
because probes cannot run tests. **I authored T013 in round 031 without running that check.**

So the reds are **excused** and correctness is scored on the implementation, which I read line by line and found
right. That follows round 016's precedent, where T008's red was "my own test's fault, not the probe's".

**Why I am NOT relaxing these tests, unlike round 016.** There, the freeze was a single equality that could become
`assert_gte` while preserving the invariant. Here the tests would have to *drive* a confirmation dialog that does
not exist in `main` — T013's implementation is a measurement and is never landed (§"Out of scope"). Rewriting six
assertions to accommodate an unimplemented feature would be weakening tests with nothing red to justify it, which
`CLAUDE.md` forbids. **The freeze is real and unfixable from where the loop stands.**

### The authoring rule this yields, and it explains two earlier tasks

> **A task that CHANGES existing, tested behaviour cannot be cleanly solved in this harness.** It will always
> redden the tests that pin the old behaviour, and probes do not author or update tests (round 022). Prefer
> **ADDITIVE** tasks — a new part, a new region, a new field, a new readout — which add behaviour without
> contradicting an existing assertion.

Three cases now support it, and the fit is exact:

| task | changes tested behaviour? | outcome |
|---|---|---|
| **T002** ("pause menu remembers the row") | yes — `test_pause_menu_is_keyboard_navigable` pinned "open() focuses Resume" | **too_hard**, discarded round 011 after 3 attempts |
| **T008** ("star bonus for a clean run") | yes — two tests pinned `stars_gained == stars_for_placement` | unwinnable for six rounds; rescued in 016 only because the freeze was one relaxable equality |
| **T013** ("confirmation before starting") | yes — six assertions pin the immediate commit | unwinnable-clean, and not relaxable |

Every additive task in the bank (T001, T003, T004, T005, T009, T011, T012) has been scoreable on correctness;
**all three behaviour-changing ones hit a frozen assertion.** That is not a coincidence, and it is a rule for
authoring the next task rather than a fact about this codebase.

**T013's correctness axis is therefore harness-limited by construction.** It is NOT `too_hard` — it produced two
real codebase findings in two rounds (round 031's silent touch dead end, and this round's confirmation that the
commit-point label works) — but it can never score a clean solve, and it is marked accordingly so no future round
spends attempts chasing one.
