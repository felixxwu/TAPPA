**It is grounded in code I read, not guessed at** (CLAUDE.md's rule for new specs). The task is genuinely
unimplemented: `lobby_field.gd::readout_for` computes exactly **one** gap — to the chaser when the player
is leading, to the car ahead otherwise — and passes four values to
`Hud.show_position(position, field, gap_ms, leading)`. A non-leader has no behind-gap at all.

**Why this task rather than a tidier one:** it crosses three things the loop has never measured together,
and every trap in it is **already documented in-file**, so the task doubles as a test of whether those
notes work:

1. **A documented arithmetic trap.** `lobby_standings.gd` opens with a UNITS block: `progress_m` metres,
   `speed_mms` millimetres/second, so metres -> ms is `* 1_000_000 / speed_mms`, "**NOT** the intuitive
   `* 1000`", and — the sentence that makes it a perfect probe — "a 1000x slip here still looks almost
   right on a slow car, which is exactly why it would ship."
2. **A deliberately asymmetric existing implementation.** The leading branch divides by the *chaser's*
   speed; the trailing branch by *mine*. A correct behind-gap must divide by the car-behind's speed and
   guard a zero.
3. **A duck-typed HUD boundary with NO arity checking.** `stage_manager.gd` builds `_hud_can` from
   `has_method(m)` alone, so widening `show_position`'s signature leaves the guard green and breaks the
   call at runtime — with two call sites to update.

## PREDICTIONS, before dispatch

1. **It calls `LobbyStandings.gap_ms` rather than re-deriving the conversion.** The units block is
   prominent and at the top of the file it must read. **Refuted if it writes its own `* 1000`.**
2. **It gets the divisor wrong** — using the player's speed for the behind-gap by symmetry with the
   trailing branch, rather than the car-behind's. This is the subtle half, and nothing states the rule
   directly; the existing code only demonstrates it.
3. **It does not update both docs** — 1 of 2 at best, matching the 1/2 results of rounds 022 and 024.
4. **No test written** (settled round 022), which matters more than usual here because `readout_for`'s own
   comment advertises testability ("Pure so the test can pin the gap conversion without a scene").

Prediction 2 is the one I most want to be wrong about: if a probe infers the divisor from the surrounding
code's asymmetry, that is evidence a *demonstrated* pattern can carry a rule that no note states.

## Fix — an executable guard that a test DOUBLE cannot silently drift from the real HUD

The cause is specific: `has_method()` ignores arity, so a widened HUD method leaves `_hud_can` green and
fails only when the call runs — and in tests the attached HUD is `StubHud`. A note would be the wrong
instrument here; this is exactly §2.6's case for an executable check.

**`test_script_breadcrumbs.gd` -> `test_stub_hud_matches_the_real_hud_signature_for_every_duck_typed_method`.**
It reads three sources and compares arities:

- the **method names come from `stage_manager.gd`'s own `for m in [...]` block** — the exact duck-typed
  boundary — so adding a method there covers it automatically, with no list restated in the test;
- the arities come from `hud.gd` and from `StubHud` in `test_stage_manager.gd`;
- it also fails if `hud.gd` lacks the method, or if `StubHud` does not implement one `_hud_can` will happily
  report as callable.

All **ten** methods match on main, so it ships with **zero exemptions** (§2.6a's ideal), and it guards its
own premise — if the `for m in [...]` block is restructured, it fails saying *the guard* needs updating.

**Validated in both directions:** clean on main (all ten found, no false mismatch); against the probe's tree
it reports `show_position: hud.gd takes 5 arg(s), StubHud takes 4`.

### Two things I got wrong while building it, both fixed

1. **I first put the guard in `test_stage_manager.gd`, and it never ran.** The arity break triggers a Godot
   debugger break mid-run, which halted GUT before reaching a test appended at the end of that file. **A
   guard must not be reachable only *after* the failure it diagnoses.** Relocated to
   `test_script_breadcrumbs.gd`, which instantiates nothing and scans source, so it always executes — and
   that reasoning is now written into the guard's own comment so the placement is not "tidied" back later.
2. **My first failure message asserted something false** — that the drift "does NOT show up as a clear
   error". The engine *does* raise `Invalid call to function ... Expected 4 argument(s)`; my earlier grep had
   filtered that line out. The honest description, now in the message, is that it surfaces as a debugger
   break attributed to whichever test was mid-flight, so *what you see first* is two unrelated-looking
   stage-manager assertions. A guard that ships a false claim is the rot this loop exists to remove.

**Durability (§2.6a): ratchet, tier 1**, derived from the source, zero exemptions, covers methods not yet

**§D4 generalisation:** it protects **every** method on the `_hud_can` boundary, not `show_position` — and
