## The cause: `is_lifting_off()` is TRUE while BRAKING, and nothing says so

The probe reasoned carefully about every state it had been warned about — fuel cut, mid-shift,
declutch, rev-limiter bounce, turbo drag — and got all of them right. It missed the one state nothing
warns about: **braking is a lift-off state.** The driver's foot is off the throttle while braking, so
`is_lifting_off(throttle)` is true, and a multiplier gated on it silently rescales engine friction
during every brake application — which is what moved `test_brake_lockup`.

Round 009 created `is_lifting_off()` precisely to be "the searchable throttle-position-only predicate",
and its comment says exactly that. **That comment is accurate and still insufficient**, because knowing
it is "throttle position only" does not tell you that the brake pedal is orthogonal to it — the name
reads as "coasting", and coasting is what a reader pictures. There is no `is_coasting()` seam (off
throttle AND off brake) for a feature that wants the coasting case specifically.

This is the same shape as the `rally_id` collision in round 017: a predicate whose name describes a
narrower situation than the one it actually matches, with the gap invisible at the call site.

## Loop B fixes

### Fix 1 — the misleading word at the predicate

`engine.gd::is_lifting_off()`'s docstring opened *"Is the driver OFF the throttle — i.e. **coasting** /
lifting off / on engine braking?"*. "Coasting" means both pedals up; this predicate is true with the
brake buried. The comment was actively teaching the misreading. Rewritten to:

- drop "coasting" and say **"THIS IS TRUE WHILE BRAKING"** in its own paragraph, with the reason
  (`engine.gd` has no brake input — `brake` appears once in the file, for the handbrake declutch);
- state the consequence and the check: drag gated on this "applies during EVERY BRAKE APPLICATION too,
  and engine drag on the driven axle changes wheel lock-up";
- **name the guard by test file and test name** (`test_drivetrain.gd -> test_brake_lockup`) — the lever
  rounds 018/019 confirmed;
- name what the observed attempt got *right*, so the note reads as "this one state is the trap", not as
  a general warning to be careful;
- and say what to do instead: there is no `is_coasting()` seam, and making one means plumbing the brake
  input through from `car.gd`.

**Durability (§2.6a): tier 4, a point-of-use note — with the structural option recorded and
deliberately not taken.** The layer-1 fix is a real `is_coasting(throttle, brake)` seam, which requires
threading brake state into `engine.gd` — an API change with wide blast radius, in a round running under
`fast` with no full-suite run. This cause has appeared **once**, so §2.6's escalation ladder puts
layers 2–3 first and reserves restructuring for a repeat. **If a future round sees this cause again,
that is the mandatory structural fix** and I have written it down so the next round does not
re-derive it.
