### Fix after attempt 2 — the RUNTIME half that round 014 never shipped

**Cause:** the same one round 014 diagnosed — a persisted key written without being declared in
`_default_profile()`. Round 014 fixed it at **layer 3 only** (a CI test). §2.6 is explicit that
for a *silent* failure a test alone is half a fix ("detection, not prevention"), and that when a
convention has failed twice the next move must be executable rather than a third note. It has now
failed twice, by two independent probes.

**What I landed — layer 2, runtime loudness (`save_manager.gd`):**

`save()` now calls `_warn_undeclared_profile_keys()`, which `push_error`s once per key for any
top-level profile key that code wrote without declaring. The message names the key and hands back
the fix ("add it to `_default_profile()` … no `SCHEMA_VERSION` bump is needed, the key backfill
handles it").

**The design problem worth recording, because the naive version is wrong.** Comparing `profile`
against `_default_profile()` alone produces **false alarms on real players' saves**: load
backfills missing keys but **never prunes extra ones** (`_migrate`, then `_sanitise`, which prunes
inside `inventory`/cars but not top-level), so an old profile can legitimately carry a retired
key. So "known" is **declared keys ∪ keys-as-loaded**, snapshotted by
`_note_known_profile_keys()` at all five `profile = …` assignment sites. Anything in `profile`
that was neither declared nor in the file is, by elimination, a key **code wrote this session** —
which is exactly the defect and nothing else.

Split into a pure `_undeclared_profile_keys() -> Array[String]` plus the `push_error` wrapper, so
the logic is testable without provoking an engine error.

**Durability (§2.6a): ratchet, tier 1 + tier 2.** Tier 1 — two new tests
(`test_a_code_written_undeclared_profile_key_is_detected`,
`test_a_retired_key_already_on_disk_is_not_reported`), the second pinning the false-alarm
behaviour so a later "simplification" to declared-keys-only goes red. Tier 2 for the mechanism
itself: it is derived from `_default_profile()` at runtime, so **every future key is covered with
no edit to anything** — the opposite of the enumerated list §2.6a warns about.
