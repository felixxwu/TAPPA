## Failure causes (taxonomy)

1. **The docs/tests-in-the-same-change convention is stated everywhere and obeyed
   nowhere (×5, dominant, REPEAT rounds 001–005).** No probe has written a test in
   five rounds — the count is still zero. Round 005 is the round that explains why,
   because T004 and T002 isolate the mechanism: T004 followed the `# Docs:` half of
   its breadcrumb precisely and ignored the `# Tests:` half of the *same comment
   block*; T002's breadcrumb spells out "every menu change needs a keyboard+gamepad
   nav test" in-line and was ignored anyway. The asymmetry is structural — Docs
   names two files and the action is additive; Tests named five to twelve files with
   no indication which pinned the behaviour, so obeying it means opening each and
   scanning for a conflict.
2. **An existing assertion that contradicts your change is undiscoverable without
   running the suite (×2, T002 + T004) — and probes are forbidden from running it.**
   Both shapes appeared: T004's went red, T002's stayed green *incidentally* and
   quietly became order-dependent. The second is worse, because a green suite
   actively confirmed a change that had just contradicted a documented contract.
3. **`game_config.gd`'s literals read as the tuning surface, and `.tres` sparse
   authoring makes it impossible to tell from the script whether an edit is live
   (×1, T006 — NEW).** A `.tres` stores only non-default values, so from the script
   there is no way to see that `drag_coefficient` is authored while
   `engine_friction_slope` is not.
4. **A value overwritten downstream, warned about only at the end of a
   200-character trailing comment (×1, T006 — NEW).** `engine_friction_base` is
   re-seeded per-engine by `EngineLibrary.apply`; the note saying so sat in the
   least-read position on the line, and half the probe's edit was inert.
5. **A local's name hides a gate, and the block it guards owns all the reward logic
   (×1, T008 — NEW).** `record_completion := top3 or opening_first` reads as "the
   player finished"; anything dropped into its ~60-line body inherits a podium gate
   its author never wrote and cannot see from the insertion point.
6. **One boolean doing two unrelated jobs (×1, T008 — NEW).**
   `damaged := _car_instance_id >= 0 and hp_lost > 0.0` conflates "was hurt" with
   "we have somewhere to record it".
7. **Reward amounts are `const`s in `rally_library.gd`, teaching every new reward
   to be one (×1, T008 — CONFIRMS backlog item 4, now sharpened).** The three
   existing star amounts sit in a commented "star scoring" block that reads as an
   invitation. A rule in `CLAUDE.md` cannot beat a local pattern this strong.
8. **One fact duplicated across two feature docs with no pointer (×1, T001 —
   REPEAT of backlog item 7, now observed twice).** Both
   `features/upgrade-catalogue.md` and `features/drivetrain-and-tires.md` narrate
   the tyre slot's contents; the probe updated one and left the other saying the
   slot holds two parts.

## Durability pass (§2.6a — new step, added to the skill this round)

The user pointed out mid-round that a fix applied to today's files is worthless if
tomorrow's files skip it: "adding the breadcrumbs to each file is good, but it's
useless if every new file doesn't have breadcrumbs." That is exactly what Fix A
shipped as first written — the guard validated existing breadcrumbs (they must
resolve, they must stay within the cap) and said nothing about a script created
tomorrow. Same half-fix shape as round 003, one layer up.

`SKILL.md` gains **step 8a / §2.6a**, a mandatory pass after the fix step: for each
fix, name what carries it forward to files that do not exist yet, ranked
enforcement test > structural impossibility > copyable sibling > point-of-use note >
`CLAUDE.md`. It introduces the **sweep vs. ratchet** distinction, requires a
durability line per fix in the report, and specifies the **baseline-allowlist
ratchet** for the awkward case where a property should hold for all future files
but does not hold for all current ones. §2.11 now refuses to file a fix under
"Fixed" if its durability line reads "nothing".

### The breadcrumb ratchet

97 of 179 scripts predate the convention, so "every script must have a breadcrumb"
cannot simply be asserted. Instead the 97 are frozen into `BREADCRUMB_BASELINE`
inside `test_script_breadcrumbs.gd`, and two tests turn that list into a ratchet:

- **anything not on the list must comply** — so every new script complies by
  default, with no rule to remember and no reviewer needed to catch it;
- **anything on the list that has since gained a breadcrumb must be removed from
  it** — so the list can only shrink and cannot quietly absorb new violations.

**Verified by negative test, not by assumption.** A throwaway
`scripts/zz_ratchet_probe.gd` with no breadcrumb was created; the suite went red
with the intended message naming the file and telling the author what to write.
The probe file was then deleted and the suite returned to green (5 tests, 681
asserts). A guard nobody has watched fail is a guard nobody knows works.
