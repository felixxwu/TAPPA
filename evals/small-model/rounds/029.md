## THE HEADLINE: docs 0/2 under the BEST possible breadcrumb condition — round 028's finding was over-read

I predicted 2/2 (weakly) because every file the probe had to edit carries a `# Docs:` breadcrumb and between
them they name both required docs. It scored **zero**. So the strong reading of round 028 — "the breadcrumb
mechanism is what works" — is **wrong**, and the surviving explanation is **dilution**:

| round | docs owed | distinct docs named across the edited files' breadcrumbs | result |
|---|---|---|---|
| 028 | 1 | **1** (`cloud-save.md`) | **updated** |
| 029 | 2 | **5** (`hud.md`, `stage.md`, `multiplayer-lobby.md`, `sfx.md`, `todo/audio.md`) | **none** |

Four files each naming two or three docs adds up to five distinct targets, and none of them moved. That is
**round 005's lesson recurring in a new place**: it capped the `# Tests:` half because "a breadcrumb naming
SIXTEEN test files is not a pointer, it is a haystack", after watching a probe follow the Docs half (two files,
obvious action) and ignore the Tests half (five files, no indication which mattered). **The same dilution now
demonstrated for the Docs half — and across files, not within one line.**

> **Revised statement: what works is a SINGULAR pointer at the point of edit. Round 028's breadcrumb worked
> because it named exactly one doc, not because it was a breadcrumb. Five docs named across four edited files
> is noise, and produces the same zero as a trailing prose clause.**

### I nearly shipped a fix for the wrong hypothesis — and the better one is simpler

My first move was to cap the `# Docs:` half the way round 005 capped `# Tests:`. I measured first: of 107
breadcrumbs, **86 name exactly one doc**, 15 name two, 4 name three, and `game_config.gd` names **six**. So a cap
would be reasonable hygiene.

But the dilution here was **across files**, not within a line, and a per-breadcrumb cap barely touches that. So
before building it I tabulated every doc result the loop has, against **the size of the code change**:

| round | task | scripts edited | docs owed | docs updated |
|---|---|---|---|---|
| 023 | T004 | **1** | 2 | **2** |
| 028 | T012 | 2 | 1 | **1** |
| 022 | T006 | 2 | 3 | 1 |
| 024 | T009 | 3 | 3 | 1 |
| 026 | T011 | 5 | 2 | 1 |
| **029** | **T011** | **4 + a test file** | 2 | **0** |

> **Doc compliance tracks the SIZE of the code change, not how the docs are pointed at.** A one-script change
> updated *two* docs unprompted (round 023 even found a doc the rubric did not list). A five-script change
> updated one. A four-script change plus a test-file reconciliation updated none.

That subsumes the breadcrumb result without contradicting it: round 028's win was a **two-script** change, which
is exactly where compliance is still high. It also matches round 010's independent read of T003 ("best read is
budget/scope truncation") from a completely different direction, and it explains why every intervention on the
docs axis has produced "usually partial" — the interventions were fighting the wrong variable.

**So I did NOT ship the cap.** §2.6 is explicit that inventing a fix destroys a round's finding, and round 018
taught me this specific lesson — I dropped a designed structural fix there when the probe refuted its premise.
The cap is recorded as a **candidate** (naming six docs in one breadcrumb is a haystack regardless), not as this
round's fix. **Stated honestly: the size correlation is n=6, correlational, and confounded** — bigger code
changes are also the harder tasks. Testing it needs a task where the same doc obligation sits behind a one-file
and a four-file variant, which is a deliberate experiment, not something to infer from here.
