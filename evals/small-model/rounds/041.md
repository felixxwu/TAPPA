### THE DEFECT: the authored effect key is not registered, so the wet tyre does NOTHING in the rain

The probe authored `"tire_rain_grip_mult": 1.20` on the part, and added the `@export` and the
`TIRE_SURFACE_AXES` row — but **never added the `EFFECTS` row**. Both siblings have one
(`tire_snow_grip_mult` and `tire_tarmac_grip_mult`, at lines 545 and 548).

Traced the consequence rather than assuming it. `apply()` does:

```gdscript
var desc: Dictionary = EFFECTS.get(key, {})
match desc.get("op", ""):
```

With no row, `desc` is `{}`, `op` is `""`, the `match` selects no arm, and the value is **never written
to the config**. So the part delivers its 1.08 flat term and its 0.83 tarmac penalty (both registered)
and **no rain bonus at all** — it is strictly worse than `race_tires` on every surface including wet,
and the one thing the task asked for does not happen. The feature is silently dead.

### Why the existing guards do not catch it — I checked instead of assuming

- **Round 001's `_cfg_set` guard** (`push_error` on a field the config does not declare) is the closest
  thing and does NOT fire: the field *does* exist, because the probe correctly added the `@export`.
  The value never reaches `_cfg_set` at all — it is dropped one level earlier, at the `EFFECTS` lookup.
  The round-001 comment even says this failure mode is silent and "no gameplay test fails"; it guards
  the *write*, not the *registration*.
- **`test_every_grip_feeding_effect_field_is_read_by_the_physics`** iterates `EFFECTS`, so a key that is
  absent from `EFFECTS` is invisible to it by construction.
- `grep 'EFFECTS.has\|EFFECTS.keys()' tests/headless/*.gd` finds **nothing**. There is no test asserting
  that every effect key authored in `UPGRADES` has an `EFFECTS` row.

**This is an unguarded, silent, feature-killing defect in the authoring path — exactly the class of
failure this loop exists to find.** It is also cheaply and legally guardable (see the fix below).

## Attempt 1 → the fix. Three layers, and only ONE of them can reach a probe

Cause (§2.5): **a silent registration seam — getting three adjacent edits right makes the fourth easy to
believe done.** The probe was not careless; it was thorough on every surface it knew about. Nothing in
the code said the axis registry and the effect registry are different registries.

**Layer 1 — enforcement test (durability tier 1).**
`test_upgrade_library.gd -> test_every_authored_effect_key_is_registered_in_the_effects_table`. Walks
`UPGRADES`, and for every key in each row's `effect` asserts `EFFECTS.has(key)`. CLAUDE.md-legal: it
iterates the whole table as opaque input and asserts a **structural contract**, never an authored value,
so retuning cannot break it. Carries a vacuous-pass guard (`assert_gt(checked, 0)`), because a parse that
silently matched nothing would be worse than a failure.

**Layer 2 — runtime tripwire.** `apply()` now `push_error`s and skips when a key has no `EFFECTS` row,
naming the part and the key and stating "the value is IGNORED and the part does nothing". This mirrors
round 001's `_cfg_set` loud-write in the same file, and covers the editor/play path where no test runs.

**Layer 3 — point-of-use note (tier 4), sited deliberately.** Put at
`GameConfig.TIRE_SURFACE_AXES`, headed **"REGISTERING AN AXIS HERE DOES NOT REGISTER THE EFFECT"**, and
it states the count plainly: *a new tyre axis is FOUR edits, three here and one in upgrade_library.gd.*
Two placement decisions worth recording:
- **NOT in the tyre-slot note**, which is already ~45 lines and which round 040 explicitly declined to
  grow further without cause. Adding here would have tested the ceiling §2.6 warns about for no reason.
- **At the axis registry**, because that is where a probe authoring a new axis is actually working, and it
  serves any new-axis task rather than only tyre tasks. This uses the two mechanisms with a confirmed
  record — a rule at the site of the edit, and contradiction-of-a-natural-assumption beating a reference.

**§D4 generalisation — which OTHER task does this serve?** T009 is the probe here, but the guard is
task-blind: it fires for **any** part authoring **any** unregistered key, so it covers the nitrous, aero,
turbo and gearbox effect families identically. Concretely it would have caught **round 021's T001 probe**
had that one skipped the row (see below), and it protects every future "add an upgrade" request. The fix
is a ratchet, not a note aimed at one request.
