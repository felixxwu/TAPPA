### Cause (§2.5) — `hidden coupling` of the worst kind: one identifier, two meanings, 110 lines apart

`_resolve_results()` runs from line 779 to ~1050. Within it:

- `rally_id` at 779–940 means **`func rally_id() -> String`** (a Callable, silently).
- `rally_id` at 941+ means the **local String**, `var rally_id := String(_rally.get("id", ""))`.

A small model editing the middle of that function has no way to know which half it is in, and the
wrong answer is not a compile error it can attribute — it is a `Callable` that type-checks nowhere
useful. This is exactly §3's "optimise for local reasoning": the unit of understanding here is
270 lines, and the same token means two things inside it.

**Note what this reveals about the loop's blind spot.** Sixteen rounds have attacked doc placement,
naming, gates and schema conventions. **No round has attacked function length**, and this is the
first failure where length is the direct enabler — a probe that got everything conceptually right
was defeated by where in a long function it happened to type.

### Correction to my own diagnosis above

I first wrote that the two meanings of `rally_id` were "110 lines apart **in the same function**".
That is wrong and I am correcting it because it changes the mechanism. Measured from the source:
`_resolve_results()` (779–~928) declares **no** local `rally_id` at all. The locals live in the
**neighbouring** functions — `_award_podium_rewards` (937) and `_is_opening_first_attempt` (1113).

So the real mechanism is **cloning a neighbour**, which is round 011's finding and a stronger
explanation than function length: reading the sibling functions shows `rally_id` used as a plain
bare identifier, which reads like a member of the class. The probe copied that idiom into a third
function where no such local exists, and the name silently bound to `func rally_id()`.

Function length is still a contributing factor and remains recorded as a deeper cause, but it is
not what fired here.

## THE POSITION HYPOTHESIS IS REFUTED ON ITS PRE-REGISTERED METRIC

I wrote the refutation condition in advance: *"treatment does no better than control."* On the
metric I registered before either arm ran, **treatment scored exactly what control scored: 0 of 3.**

**And the reason it is refuted is more informative than the refutation.** The treatment probe

code comment that is almost a paraphrase of the note's final clause:

| the note says | the treatment probe did |
|---|---|
| "leaving a new one ungated is a choice, so **say why in a comment** if you make it" | wrote exactly that comment, justifying ungated in 4 lines |
| "Docs: `features/upgrade-catalogue.md` AND `features/drivetrain-and-tires.md`" | **ignored — neither touched** |
| "the row, the docs, **the tests**" | **ignored — no test** |

So the note was read and **partially obeyed, clause by clause**: the clause asking for an edit
**inside the file it was already editing** was followed; the clauses asking it to **go and edit
other files** were not. That is the same boundary rounds 012 and 013 hit from the other direction
(round 013's probe read `menu-navigation.md`, cited it by line range, and edited nothing).

**The corrected statement of the lever, which is narrower and more useful than what I had:**

> Position determines whether a note is READ. It does not determine whether an agent will leave the
> file it is working in. In-file obligations (name it this, justify that, use this shape) are
> movable by placing them at the edit site. Out-of-file obligations (update two docs, add a test)
> are **not** movable by position, and this loop has now failed to move them by: splitting the doc
> (012), making the doc necessary to read (013), writing falsifiable statements (015, mixed), and
> relocating the checklist to the insertion point (017).

Four independent interventions, four failures on the same axis. **That is the harness-limited
conclusion (§2.4) arrived at from a fourth direction, and it should now be treated as settled for
out-of-file obligations rather than re-attacked.**

### Fix following the refutation — the note becomes an executable check

§2.6 is explicit: a note that has failed is not answered by another note. The tyre-doc obligation
has now failed **four** interventions (round 012 split the doc; 013 made it necessary to read; 015
wrote falsifiable statements; **017 moved it to the insertion point and watched the probe read it
and still skip the docs**). So it becomes a test.

**`test_upgrade_library.gd` -> `test_every_tyre_slot_part_is_documented_in_the_tyre_doc`.**
`features/drivetrain-and-tires.md` **enumerates the slot's contents by id** ("the `tires` upgrade
slot holds the tyre compounds — **Snow Tires** (`snow_tires`, …) and **Race Tires**"), so a third
compound leaves it silently incomplete — which is round 009's recorded failure verbatim.

Design decisions worth recording:

- **Reads the authored table from the SOURCE FILE**, not `UpgradeLibrary.UPGRADES`, because this
  file's `before_each` installs `UpgradeFixtures` — the doc must describe what *ships*.
- **Zero exemptions** (both current tyre ids are documented), so the list cannot rot (§2.6a's ideal).
- **Guards its own parse**: if fewer than 2 tyre parts are found, it fails saying *the guard* needs
  updating rather than passing vacuously — the failure mode a source-scanning test is most prone to.
- **Deliberately narrow, and here is the evidence for that choice.** I first tried the broad version
  — every `UPGRADES` id must appear in `features/upgrade-catalogue.md` — and measured it: 9 of 10
  pass, and the one failure (`aero_kit`) is a **false positive**. That doc covers the part
  thoroughly as "Aero Kit" and simply never writes the id. A repo-wide id-in-doc check would flag
  correct prose and would have needed a permanent exemption on day one. Narrow and true beats broad
  and noisy — and this is exactly the brittle-guard trap §2.6a warns about, caught by measuring
  before shipping.

**Validated both directions:** passes on main (`snow_tires`, `race_tires` both documented); against
the treatment arm's tree it reports `UNDOCUMENTED=['gravel_tires']`. So it catches the exact miss
both arms of this round's A/B made.

**Durability (§2.6a): ratchet, tier 1.** Derived from the authored table, so a tyre compound added
tomorrow is covered with no edit to the test.

**§D4 generalisation:** it serves **T009** ("wet-weather tyre compound") directly — the same slot,
