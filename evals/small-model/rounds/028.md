That is a real result for the repo's oldest convention. Set against the rest of the loop's doc evidence:

| form of the pointer | outcome |
|---|---|
| trailing prose clause naming two docs (T001 pre-018, T010's audio hook) | ignored |

| **`# Docs:` header breadcrumb naming ONE doc, in the file being edited** | **updated** |

**One doc, named in the header of the file you are already editing, is the strongest version of this lever seen
so far** — and it is also the cheapest, which is why round 003 built it. Its weakness is equally clear: it names
the *file*, not the *obligation*, so it cannot express "and also the other doc" (which is where the two-doc
cases keep failing).

### The one defect: an invented example value

The probe wrote `# The device name (e.g. "iPhone", "Desktop") that last synced this profile.` and put
`"from iPhone"` in the doc. **`FirebaseConfig.device_tag()` returns `"web"` or `OS.get_name().to_lower()`** — so
`"macos"`, `"windows"`, `"linux"`, `"android"`, `"ios"`. It **never** returns `"iPhone"` or `"Desktop"`.

So a reader of the doc now believes the screen shows "from iPhone" when it shows "from ios". This is round 003's
invented-asset-path failure in a milder form — plausible-looking values that the code cannot produce — and it
lands in the **doc the breadcrumb just successfully steered it to**, which is a useful caution: getting a probe
to the right file does not make what it writes there true.

Scored on **convention** rather than correctness: the user-visible string is built from the real value, so the
behaviour is right; what is wrong is the illustrative text. Convention 2 (up from round 027's 1 — a doc was
updated at all) rather than 3.

## Fix — state the exact value set where the value is produced

The probe invented `"iPhone"` because nothing said what `device_tag()` returns. Its own docstring explained the
*purpose* ("so the conflict prompt can say 'from android'") but never the **set** — and that value is shown to
the player, so a consumer formatting or documenting it needs to know its real shape.

Added at `FirebaseConfig.device_tag()`:

> "THE EXACT VALUES, because this string is shown to the PLAYER and every one of them is lowercase and terse:
> `"web"`, or `OS.get_name().to_lower()` — i.e. "macos", "windows", "linux", "android", "ios". There is no
> title-case or friendly form anywhere: it is NOT "iPhone", "Desktop" or "Mac". … (Written down because an
> attempt at a new device readout documented the screen as showing "from iPhone", a value this function cannot
> return.)"

It also says what to do instead — a UI wanting a prettier label must map it deliberately rather than assume one.

**Durability (§2.6a): tier 4, a point-of-use note, and honestly labelled.** The stronger options do not apply:
a guard cannot assert what a *comment or doc* claims about a value without pinning prose, and the value set is
`OS.get_name()`'s, which the project does not control. What makes this the right placement anyway is the loop's
best-confirmed finding — **rules about the code in front of you land** (round 027's `updated_utc` rule reached a
probe in a 480-line module it had never seen). This one sits on the function a consumer must call.

**§D4 generalisation:** the tag already reaches the player through `conflict_summary`'s `cloud_device`, which the
conflict prompt displays, so any future readout or label of it is served — not just T012.

## Verdict

**CONTINUE.**

**1. The repo's oldest convention works, and this round is the first clean measurement of it.** A `# Docs:`
breadcrumb naming ONE doc, in the header of the file being edited, moved the doc where the same task with no
breadcrumb scored 0/1 one round earlier — with clean attribution, because the other edited file still has no
breadcrumb. That retires a question the loop has circled since round 003, and it sharpens the docs picture:
**one doc named in the header of the file you are editing is the strongest and cheapest form; the weakness is
that it names a FILE, not an obligation, so it cannot say "and the other doc too" — which is exactly where the
two-doc cases keep failing.**

**2. "Adjacent correct sibling" is now n=3** and has never failed: two different probes, two different variable
names, both setting the new field correctly in both sync paths because `last_sync_utc` already is.

**3. Getting a probe to the right file does not make what it writes there true.** The breadcrumb steered it to
`cloud-save.md`, where it documented a value the code cannot produce. Fixed at the source of the value.
