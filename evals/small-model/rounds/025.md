## THE ROUND'S REAL FINDING: a point-of-use note was CONSUMED AND DELETED by the change it guided

This failure mode is new to the loop and worth stating carefully.

The AUDIO HOOK comment was written as a **placeholder marking where a feature should go** ("the countdown
beep / GO sting belongs here"). The probe implemented the feature at that spot and **deleted the whole
comment as if it were a TODO it had discharged** — obeying its code instruction on the way out.

**Why that is a real loss, not tidy-up:** the comment was the only place in the file carrying

- the hard prohibition **"DO NOT hand-roll an AudioStreamGenerator, AudioStreamPlayer or PCM loop in this
  file"** — the exact mistake that scored round 008's probe **2/0/0/0** and took a whole suite down;
- the reason (`Audio` owns the SFX bus, the headless guard, and the `play()`/`get_stream_playback()`
  order);
- the pointers to `features/sfx.md` and `todo/audio.md`;
- and guidance for the cues **still unwired** — impact/wreck, UI clicks, the podium sting.

So implementing *one* of four planned cues destroyed the guidance for the other three, and re-opened the
door to the loop's worst recorded failure. **A note phrased as a placeholder invites its own deletion.**
The durable form is a **standing rule about the file or subsystem**, which remains true after any one call
site is filled in.

## Fix — the hook becomes a STANDING RULE that cannot be mistaken for a TODO

`stage_manager.gd`'s `# AUDIO HOOK` block is now `# AUDIO RULES FOR THIS FILE`, rebuilt on three findings
from this round and rounds 018/019:

- **Self-preserving, and it says why.** It opens: "these hold whether or not any cue is wired yet, so do
  NOT delete this block when you add one. It is not a TODO marker; a probe read it, implemented the
  countdown beep at this exact spot, and removed it, which took the prohibition below and the doc
  pointers with it while three cues were still unwired." Naming the observed deletion is what makes the
  instruction credible rather than fussy.
- **Numbered, not prose** — the form rounds 019/021 confirmed. Part 1 the DSP prohibition (with the
  consequence: "took the whole stage-manager suite down"), part 2 the timing rule, part 3 the docs.
- **Part 2 is the timing fix, stated as the property and the failure:** "KEY A PER-COUNT CUE OFF THE
  DISPLAYED INTEGER, not off crossing a float threshold… Detecting crossings gives you a **silent first
  count** and, at zero, a tick and the GO cue **in the same frame**. Track the last displayed value and
  fire when it CHANGES." That is rounds 019/020's lesson applied — state the invariant *and* the concrete
  failure a compliant-looking answer still hits.
- **Part 4 lists the cues still unwired** (impact/wreck, UI clicks, podium sting) and says the block
  outlives any one of them being finished — so the reason not to delete it is visible in the block itself.

**Durability (§2.6a): tier 4, a point-of-use note — and honestly labelled.** The stronger options were
considered and rejected:

- **A guard test is not available.** The behaviour it would assert does not exist in `main` — T010's
  implementation is a *measurement*, never landed (§"Out of scope") — so there is nothing to test. This is
  a genuine structural limit of this task, not laziness.
- **A guard against deleting the comment** would be a test asserting a comment's presence, which pins
  prose and rots on the first legitimate rewording.

**Prediction, on record:** a future T010 probe beeps once per displayed count (four cues, no doubled GO)
and leaves the AUDIO RULES block in place. **Refuted if it deletes the block again or re-ships the
crossing bug** — and if the block is deleted a second time, the escalation is structural: move the
prohibition into `audio.gd`'s own API surface (e.g. a `push_error` if a raw `AudioStreamPlayer` is
constructed in a stage script) rather than relying on a comment at all.

**§D4 generalisation:** parts 1, 3 and 4 govern **every** audio call site in the file, not the countdown —
which is the whole point of the rewrite, and directly serves the three unwired cues. Part 2's
"key off the displayed value, not a float crossing" applies to any per-count or per-tick cue.
