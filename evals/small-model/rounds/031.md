### A second, silent defect the tests do NOT catch: state cleared before a re-entrant call

`hq.gd::_start_preflight(resume: Callable, …)` stores `_pending_start = resume` and returns `false` when the
player is on touch and has not yet chosen a control scheme, so the start can be **resumed after** they pick one.

Both new handlers clear their state *before* calling it:

```gdscript
_pending_challenge_start = {}          # cleared here
…
if not _hq._start_preflight(_on_challenge_start_confirmed):   # may re-enter the same function later
    return
```

and each handler opens with `if _pending_challenge_start.is_empty(): return`. **So on a touch device, a
first-time player confirms the challenge, is sent to settings, picks a scheme — and nothing happens.** The
car-park path is worse: its retry also reads `instance_id` out of the now-empty dictionary and returns.

Platform-gated (`Platform.is_touch()`), so the headless suite does not reach it — a silent dead end of the
"clear state before a call that can come back to you" class.

## Fix — document the deferred-resume contract where every caller passes it

The transferable cause is not "the probe cleared a dict". It is that **`_start_preflight`'s `resume` may be
invoked long after the call returns**, and nothing said so at the function every start path must call.

Added to `hq.gd::_start_preflight`:

> "`resume` MAY BE CALLED MUCH LATER — after the player has been to the settings screen and saved a scheme — so it
> must still work then. Anything it needs must SURVIVE that gap: **BIND** the state into the callable, the way the
> free-roam path does (`_start_preflight(_launch_free_roam.bind(instance_id, model_id), instance_id)`), or leave it
> in a member that nothing clears in between. What does NOT work is parking the state in a member and clearing it
> before calling this. …"

plus the observed failure and why the suite cannot see it (`Platform.is_touch()`).

**The shape of this fix is chosen from the loop's own evidence, not by taste.** It is (a) a rule about the code
directly in front of the caller — the placement that has worked every time it has been tried (round 027's
`updated_utc` rule, round 025's write-site gate rule) — and (b) it **names a working sibling**, which is the
lever now 5-for-5. `hq.gd:2731` already does the right thing with `.bind()`; the probe simply never saw it,
because nothing at `_start_preflight` pointed at it.

**Durability (§2.6a): tier 4, a point-of-use note — and I considered the alternatives rather than defaulting.**
A guard would have to detect "clears a member, then passes its own handler as `resume`", which is a static
analysis this project has no business carrying. A structural fix — making `_start_preflight` take the state
explicitly instead of a bare `Callable` — would change five call sites and a public-ish HQ seam to prevent a
first-occurrence bug, which §2.6's escalation ladder reserves for a cause that has REPEATED. **If this cause
recurs, that refactor is the mandated next step** and it is written down here so the next round does not
re-derive it.

**§D4 generalisation:** it governs **every** start path — career (`_proceed_with_start`), free roam
(`_launch_free_roam`), and both challenge paths — so it serves T013 and any future "start something" flow, not
this one request.
