## Fix — state the gate-id requirement where the gate is authored

Nothing in the code said the id must resolve; the protection was a test a probe cannot run. Added to the tyre-slot
procedure, at the exact field both failures got wrong:

> "**IF YOU DO GATE IT, THE ID MUST BE A REAL SPECIAL** — do not compose a plausible-sounding one. A gate naming no
> rally can never be met, so the part is **PERMANENTLY UNWINNABLE** and nothing at runtime complains; `rally_gate_met`
> just returns false forever. Two separate attempts invented `h_coast_qualifier` and `sp_coastal_challenge`, neither of
> which exists. Verify with `grep -n '"id": "sp_' scripts/rally_library.gd` … and copy one exactly. Guarded by
> tests/headless/test_rally_library.gd … — **but that is a test you may not be running, so do the grep.**"

Four things in that wording are deliberate, each from a lever this loop has measured:

- **the consequence first** (permanently unwinnable, silent) — rounds 025/031 showed naming the consequence changes
  behaviour, not just avoidance;
- **the guard named by test file and message** — rounds 018/019's confirmed form;
- **a concrete verification command**, because round 019 showed a rule needs its check, not just its statement;
- **"a test you may not be running, so do the grep"** — the probe genuinely cannot run tests, so pointing at the guard
  alone would be pointing at something out of reach. This is the first fix I have written that acknowledges the
  harness limit *inside* the instruction rather than around it.

**Durability (§2.6a): tier 4, a point-of-use note — with the executable half already in place.** The guard exists and
fires; what was missing was reachability for an author who cannot run it. I am not adding a second guard.
