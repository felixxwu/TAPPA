### But I must NOT claim the experiment succeeded — the outcome does not distinguish the mechanisms

The round existed to test whether a documented **rationale** generalises to a decision it does not literally cover:
the ONE-NAME-ONLY rule is about *names*, the task is about *stars*.

**The result is consistent with that — and is not evidence for it.** Two explanations fit equally well:

1. the rationale generalised, and the probe avoided per-pin clutter because the header explained why clutter broke
   the map; or
2. **the footer was simply the obvious place**, because `_write_footer` already renders exactly the pin the player
   is "looking at" — which is what the request says. On that reading the probe never considered painting every pin
   at all, and the rationale did no work.

**The probe's report never mentions the clutter rule**, which mildly favours explanation 2. Round 030's lesson —
*verify the mechanism of a confirmed prediction, not just its outcome* — applies directly, and I nearly wrote this
up as a win.

**So the experiment is INCONCLUSIVE, and it was mis-designed rather than merely unlucky:** I chose a task whose
correct answer was also the *convenient* answer, so the two mechanisms could never separate. A real test needs a
task where the obvious implementation is the cluttered one and only the rationale argues otherwise — e.g. a readout
that has no existing single-pin home and must therefore either go on every pin or be gated to the asked-about one.

Recording that as the design flaw it is, rather than banking a result the evidence does not support.

## Fix — the podium-gate warning never reached `best_placement()`

The probe's comment reads `if placement > 0:  # Only show if the rally has been completed`. **The code is right and
the comment is wrong**, in exactly the way rounds 015/016 spent two rounds fixing: `best_placement` is written only
by the podium-gated recorder, so `> 0` means **podiumed**, not completed — a 5th-place finish is completed and
reads 0.

Checked where the warnings actually live, and found the gap:

| read path | carries the gate warning? |
|---|---|
| `rally_podiumed()` | yes (round 015) |
| `podium_count()` | yes (round 015) |
| `podium_rally_count()` | yes (round 015) |
| **`best_placement()`** | **no** — its docstring says only "or 0 if never placed" |
| `overworld_map.gd` (the new consumer) | no reference to the gate at all |

Rounds 015/016 hardened the three *counting* paths and missed the *placement* accessor — which is the one a UI
consumer naturally reaches for. So the conflation resurfaced at a new consumer, in a different file, sixteen rounds
later. Warning added to `best_placement()`, naming what 0 does and does not mean and pointing at the recorder.

**Durability (§2.6a): tier 4, a point-of-use note.** A guard is not available — the defect is a *comment* asserting
the wrong semantics, and nothing executable can check prose. What makes the placement defensible is the loop's
best-supported finding: a rule on the function a consumer calls is the placement that has worked every time
(rounds 025, 027, 031, 032).

**§D4 generalisation:** `best_placement` is called from the map, the HQ readout box and the reward path; the warning
serves every consumer, not this one request.
