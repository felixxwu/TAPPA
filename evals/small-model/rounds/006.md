### T009: round 004's restructure has a real design defect, and the red test is mostly MY bug

I designed T009 to catch a probe cutting corners on the registry. It caught the
registry instead. The grader was asked to rule between "the probe failed to follow
an available one-file path" and "unavoidable", and returned **unavoidable**, with
the reasoning verified against the code:

- `_channel_weight(channel, tarmac_weight, snowy)` receives **only** those two
  context values. An axis keyed on weather has nothing to read.
- The one escape — reading weather off `source` — is closed **by my own test**:
  `test_a_live_config_and_a_car_meta_resolve_identically` pins that a live
  `GameConfig` (which has `weather`) and a rival's `car_meta` Dictionary (which
  does not) must resolve the same. Deriving stage context from `source` would
  break the registry's contract.
- So the registry "generalises over *which axes exist* but hardcodes its two
  context inputs". The probe's widening — an optional param defaulting to `"dry"`,
  registry structure preserved, only the two call sites that already had the value
  in hand — is, in the grader's words, "closer to correct engineering than to
  carelessness".

Three defects in my round-004/005 work, all confirmed against the files:

1. **The design cannot do what it claims** for any axis outside the surface
   dimension.
2. **The docs actively misdirect, using this exact task as the example.**
   `features/drivetrain-and-tires.md:246` — text I wrote — reads "Adding a surface
   axis (**wet**, gravel, ice, …) is three edits, all in `game_config.gd` …
   Nothing else changes." It names *wet* first, as the headline easy case the
   mechanism cannot serve.
3. **My guard test fails every correct implementation of the intended answer.**
   `test_every_registered_axis_has_a_blend_rule` probes only `(0.0, true)` and
   `(1.0, false)`, so `weather` defaults to dry and any non-surface channel reads
   as inert. Its own header advertises "Registering a wet or gravel axis … keeps
   this file green" — false for wet. **The probe was set up to ship red.**

The grader also found two defects that *are* the probe's: the arm matches the bare
literal `"rain"` rather than `RallyLibrary.WEATHER_RAIN`, so the wet compound does
nothing on `"storm"` stages, which are also wet. Correctness 1 stands. But the
cause taxonomy below assigns this failure to the codebase, where it belongs.

## Failure causes (taxonomy)

1. **Prose obligations have no executable backing (×5, dominant, REPEAT 001–006).**
   Two graders reached this independently and neither hedged. T002's breadcrumb
   spells out the nav-test requirement four lines above the function the probe
   edited, and was read past. T004's was shortened to three items plus a literal
   grep, and was read past. The T002 grader: *"A rule stated in prose, whether in
   `features/README.md:37` or inline four lines above the changed function, does
   not fire at this model class… stop investing in prose placement and start
   converting these obligations into things that go red."* Round 006 acts on that.
2. **The registry hardcodes its context inputs (×1, T009) — a defect I introduced
   in round 004**, made worse by docs that named this exact task as the easy case
   and a guard test that failed correct answers.
3. **A name that lies about its metric (×1, T005 — REPEAT of round 003, unchanged
   name, identical failure).** The strongest possible evidence that the name, not
   the model, is the cause.
4. **Assertions that pass incidentally on a shared mutable fixture (×1, T002).**
   `test_pause_menu.gd` builds one `_pause` in `before_all`; the one assertion that
   should have caught the change stayed green, and the file's own "order-safe"
   header comment silently became false.
5. **No "finished any position" concept exists in the save schema (×1, T005).**
   Nothing correct was available to reuse and no lookup fails, so the path of least
   resistance is the wrong metric.
6. **Docs quote live tunable values inline (×1, T006).**
   `features/engine-and-transmission.md:92` states the slope is **1.0** and that it
   "is not overridden in `config/game_config.tres`" — both falsified by a correct

7. **"Profile" has no UI referent (×1, T005).** See above.

## Fixes applied (main checkout, no commits)

Three fixes, chosen by frequency × cost. Two were delegated to subagents working on
disjoint file sets while I took the third; all tests were run by me afterwards.

### Fix A — the registry's context becomes data (causes 2, mine to fix)

`tire_surface_mult_for(source, tarmac_weight, snowy)` becomes
`tire_surface_mult_for(source, ctx)`, where `ctx` is built by the new
`GameConfig.fill_tire_context(ctx, tarmac_weight, snowy, weather)`. It is filled **in
place** and returned, so `drivetrain.gd` owns one scratch Dictionary (`_tire_ctx`,
declared beside `_surf_scratch`) and the per-wheel path still allocates nothing.

The context deliberately carries **weather, which no axis reads today** — that is the
whole point: a wet-weather axis is now genuinely three edits in one file.

- **Layer 1:** the failure mode (a non-surface axis forcing a signature change) is
  designed out for anything the context carries.
- **Layer 2:** `_channel_weight` now returns **NAN**, not `0.0`, for a channel with
  no arm. Zero was indistinguishable from "not on that channel right now", which is
  precisely why the old guard could not tell an unregistered channel from an
  inactive one.
- **Layer 3:** the guard test now asks `_channel_weight` directly whether an arm
  exists instead of probing for inertness, so it can no longer false-fail a
  correct axis. Plus a new test asserting the context still carries weather, so
  nobody "tidies away" the unused key and silently restores the three-file shape.
- **The doc is corrected and says what it is conditional on.** The paragraph that
  read "Nothing else changes" now states plainly that an axis keyed on something the
  context does *not* carry needs five edits across three files, and records why the
  paragraph exists.

**Durability (§2.6a): ratchet.** The NAN sentinel plus the weather-in-context test
mean both the original defect and the specific regression are detected mechanically.

### Fix B — the HUD debug set becomes data, and the test binds to it (cause 1)

The escalation the T004 grader called for. `scripts/hud.gd` gains
`const DEBUG_READOUT_NODES` — one authoritative membership list — and
`debug_readout_elements()`; both `_ready`'s initial visibility and the `_timed_process`
H-toggle now loop over it instead of naming labels in straight-line code at two sites.
Moving a label in or out of the debug set is now a **one-line membership edit**.

The bundled `test_speed_gear_rpm_hidden_until_h_toggle` — five labels and both toggle
directions in one body, with the gear contract as one unnamed line among five — is
replaced by tests bound to that same list, plus per-element contracts that carry the
element's name, including `test_gear_label_is_part_of_the_h_gated_debug_readout`.
A future change to gear's visibility now fails a test **whose name says gear**.

Behaviour is unchanged: gear is still hidden on startup and still H-gated. This is the
refactor, not the feature.

**Durability (§2.6a): structural.** The membership list is the single source of truth
and the tests derive from it, so "remember to update the test" becomes "there is
nothing to update".

### Fix C — the lying name is renamed (cause 3)

`RallyLibrary.completed_count()` → **`podium_count()`**;
`Save.completed_rally_count()` → **`podium_rally_count()`**. Both old names survive as
one-line deprecated wrappers, which is what makes the rename cheap and safe. Every
call site updated across production and tests (`reward_system.gd`,
`test_save_manager`, `test_rally_session`, `test_rally_library`), the persisted
`completed` KEY untouched so no migration is needed, and three feature docs corrected
(`save-persistence.md`, `rally-roster.md`, `reward-system.md`).

The definition now states what is NOT counted, that a 5th place leaves no trace, that
**no finished-in-any-position counter exists in the schema** so a feature needing one
must add persistence — and, bluntly, never to label UI "RALLIES COMPLETED: N" off it.
That closes cause 5 as a discoverability problem even though the missing feature is
deliberately not built.

**Durability (§2.6a): structural for the name, prose for the caveat.** The honest name
is self-propagating — a reader of `podium_rally_count()` cannot form the wrong belief.
The "no finish counter exists" caveat is prose with no ratchet, and is recorded as
such rather than filed as complete.
