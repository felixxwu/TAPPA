# Phase 3 — Renderer, build spike, go/no-go: implementation plan

**Depends on:**
- Phase 2's data: 2.1 and 2.3 are done (the `neutral` CI job in `.github/workflows/test.yml` is green, 10,734
  manifest lines match). 2.2's first publish is still waiting on the user. That doesn't block anything here,
  because the `neutral` job exports its own `.bake.bin` from the fetched `.bake.res`.
- Phase 0.6 (iOS export and signing) is **not done**. It blocks only the TestFlight half of 3.3.
- Phase 1.8 (device numbers) needs the user's real devices. It blocks only 3.5 and the gate.

This file plans steps 3.1–3.6 of `todo/2026-11-27-rust-native-migration.md` ("Phase 3 — Renderer and build spike,
and the go/no-go gate"). Read that spec's "Stack", "Renderer", "Threads", "Where the parity harness hooks in" and
"Architecture decisions" first, plus `features/neutral-format.md`. Tick the steps in the spec as they land.

The spec says Opus drives Phase 3. This plan is the Opus part. Its research and design questions are settled
below, and every work package (WP) after that is mechanical enough to give to a Sonnet agent. Escalate to Opus by
the spec's escalation rule, giving it the failing CI log, not a fresh brief.

**Constraints the plan is shaped by:**
- The user is away.
- The Mac has no Rust toolchain. GitHub Actions is the only compiler. The repo is public, so ubuntu, macOS and
  Windows runners cost nothing.
- CI has no GPU. Native rendering runs on software adapters: lavapipe (Mesa's software Vulkan) on ubuntu, WARP
  on Windows. Browser rendering runs on SwiftShader inside headless Chrome.
- Agents don't push (global rule). Every Rust check here only happens after the user, or the remote
  environment, pushes. See §7, item 1.

Each step is split into **Build now** (CI can verify it) and **Needs the user**.

## 0. Corrections and facts found while planning

- **Godot 4.6 bundles Jolt 5.4.0 at commit `036ea7b1d717b3e713ac9d8cbd47118fb9cd5d60`**, with no patches, and
  leaves out every `ENABLE_OBJECT_STREAM` file (`thirdparty/README.md` at `4.6-stable`). It is built with **no**
  `JPH_CROSS_PLATFORM_DETERMINISTIC`. `modules/jolt_physics/SCsub` defines only `JPH_ENABLE_ASSERTS` (dev builds),
  `JPH_DEBUG_RENDERER` (editor builds) and `JPH_DOUBLE_PRECISION` (double builds). It adds `-msse4.2` on web when
  wasm SIMD is on. So the spec's "if not" branch applies. The Rust build turns the option on, and the car
  tolerances have to absorb the difference. That is Phase 4's problem, but 3.2 measures how big the difference is
  (WP1).
- **No published Rust binding matches 5.4.0.** `joltc-sys` and `rolt` 0.3.1 wrap Jolt 5.0.0. JoltC itself targets
  5.1.0. `oxijolt-sys` 1.1.0 wraps 5.6.0, and its maturity is unverified. "Forkable to Godot's commit" therefore
  means writing our own shim (§1, "Physics"). That is less work than it sounds. The car is Godot's raycast vehicle
  (`scene/3d/physics/vehicle_body_3d.cpp`), not Jolt's `VehicleConstraint`, so the Jolt surface the game needs is
  small: bodies, a few shapes (box, convex hull, heightfield, mesh), ray and shape casts, a contact listener for
  `DamageModel`'s impulses, and stepping.
- **Water isn't a separate draw.** It is part of `shaders/level_ground.gdshader`, so porting the ground shader
  covers it.
- **The level world has no lights.** Only `scripts/car_card_preview.gd` and `scripts/log_pile_lab.gd` create a
  light. That confirms the Renderer section's "no shadow map pass" from the code. The car's shadow is
  `shaders/car_shadow.gdshader`.
- **The viewer can't fly "along `hafren.rec`" directly.** `benchmark/runs/hafren.rec` is a Godot `store_var`
  Variant: format 1, car poses only, `LevelReplay.STRIDE` 21. And the frame is drawn from a chase camera, not from
  the car's pose. So Godot has to export the camera's pose for every tick (WP5).
- **The viewer can't choose which terrain chunks to draw on its own.** Godot's streamer planner decides which
  chunk, at which level of detail and stitch mask, is live, and porting the planner is Phase 4 (`terrain`).
  `NeutralGeometry.export` already visits every 50 m sample of the path (`SAMPLE_M`). It also has to record the
  live chunk and cover set at each sample (WP5). The viewer then draws exactly what Godot had, and the GPU's job is
  frustum and distance culling plus picking mesh LODs.
- **Trees, buildings, the car and the sky are already in Phase 2's data.** Trees are the bake's `tree_xf`,
  `tree_tile_first` and `tree_kind`, plus `decoded_row` for visibility (`crates/assets/src/bake.rs`), and the tree
  card textures. Buildings are `.buildings.bin` with the shared atlas. The car is `car.tscn.tapn`. The sky is
  `textures/sky_field.png.tapn` (`GameConfig.default_sky_panorama`). Spectators, fences, log piles, particles and
  the HUD are left out. The Godot comparison run turns them off with `--off=` (3.5).
- **Rust WebAssembly threads need nightly.** `rust-toolchain.toml` pins stable 1.91.0. The threaded wasm build
  needs `-Z build-std=std,panic_abort` and
  `RUSTFLAGS="-C target-feature=+atomics,+bulk-memory,+mutable-globals"` on `wasm32-unknown-unknown`. So the wasm
  jobs use a second toolchain, a dated nightly (§6, question 2). Everything else stays on 1.91.0.
- **`wasm-bindgen-cli` must be exactly the same version as the `wasm-bindgen` crate.** Pin both with `=` and
  install the CLI with `cargo install --locked --version`.

## 1. Shared design

### Crates added (the spec's "Crates" table, only the rows Phase 3 needs)

| Crate | Phase 3 contents | Deps (pinned `=`, newest release at least two weeks old when the agent writes it) |
|---|---|---|
| `physics` | Only the Jolt shim and its spike tests (`src/sys.rs`, `cpp/shim.{h,cpp}`, `build.rs`). The car is Phase 4 | `cc` (build) |
| `render` | The wgpu renderer: device, buffers, the cull pass, pipelines, frame. Depends only on `assets` (the spec allows `gdcompat` too, but it doesn't exist yet and the renderer only passes Godot's 12-float transforms through) | `wgpu`, `bytemuck`, `glam`; `naga` (dev) |
| `platform` | Only what the viewer needs: window and canvas (winit), a worker pool (native `std::thread`; web through `wasm-bindgen-rayon` or `wasm_thread`, §6, question 3), a frame clock, and loading files (`std::fs` natively, `fetch` on web) | `winit`, `wasm-bindgen`, `web-sys`, `js-sys`, `wasm-bindgen-futures` |
| `app` | The `viewer` binary and wasm entry: plays the camera path, streams prebuilt geometry, writes the benchmark report, `--shot` | the above |

- `gdcompat`, `config`, `game`, `ui` and `parity` aren't created. Nothing in Phase 3 uses them.
- **Dependency guard** (the CI check the spec planned for Phase 3): `tools/dep_guard.sh` runs
  `cargo tree -p assets -p physics -e normal` and fails if `wgpu`, `winit`, `cpal` or `web-sys` appears. Later
  phases add each headless crate to that list.
- **Only `platform` may contain `#[cfg(target_arch = "wasm32")]`.** `app`'s wasm entry point is the one
  exception (`#[wasm_bindgen(start)]`).

### Physics: our own shim over Jolt 5.4.0

- Jolt becomes a git submodule at `third_party/JoltPhysics`, pinned to `036ea7b`. Every Rust job checks out with
  `submodules: true`.
- `crates/physics/build.rs` compiles `third_party/JoltPhysics/Jolt/**/*.cpp`, without the object-stream files
  (the same list Godot excludes), plus `cpp/shim.cpp`, using the `cc` crate. No CMake and no bindgen. Flags:
  `-std=c++17 -fno-exceptions -fno-rtti`, `JPH_CROSS_PLATFORM_DETERMINISTIC` (behind a feature flag,
  `deterministic`, on by default), and `JPH_OBJECT_LAYER_BITS=16`. On wasm it adds
  `--target=wasm32-wasi-threads`, `--sysroot=$WASI_SDK/share/wasi-sysroot` and
  `-matomics -mbulk-memory -msimd128`.
- `cpp/shim.h` is a flat `extern "C"` API with opaque handles. In this phase it only covers what the spike uses:
  `world_new(max_bodies)`, `world_free`, `shape_box`, `shape_heightfield(samples, n, scale, offset)` (safe to call
  from any thread), `body_add(shape, pos, rot, motion)`, `world_step(dt)`, and `body_state(id, out[13])`
  (position, rotation, linear and angular velocity). Phase 4 adds casts and contacts.
- Jolt's allocator hooks (`JPH::Allocate`, `Free`, `AlignedAllocate`, `AlignedFree`) are pointed at Rust's global
  allocator through four `extern "C"` functions. That way one allocator owns the shared wasm memory, and on wasm
  there is no wasi-libc `malloc`.
- `JobSystemSingleThreaded` and a `TempAllocatorImpl` sized like Godot's
  `jolt_physics_3d/limits/temporary_memory_buffer_size=64` (in MB, `project.godot`).

### Renderer (the spec's "Renderer" section, made concrete)

- **The device asks for `wgpu::Limits::default()`** (WebGPU's default limits) **and no optional features on every
  platform**, even natively. That way the native CI runs on lavapipe and WARP catch any use beyond what the web
  allows. This follows from "one path, designed to WebGPU's default limits" in the spec.
- **Frame:** uploads → `cull.wgsl` (one compute dispatch) → main pass at the internal resolution (sky; then
  opaque, alpha-cut, the blended few) → post (`ps1_post_process` and the horizontal stretch) → present. That is the
  spec's pass list minus UI.
- **Buffers:** vertex storage buffers per layout (terrain, static mesh, card), one instance-record buffer
  (64 bytes: transform 12 floats, mesh id, draw distance, LOD range, custom value), a mesh table, a visible list,
  and one indirect-args record per batch. `firstInstance` is always 0, and `batch_base` is passed as a
  dynamic-offset uniform.
- **WGSL shaders** in `crates/render/shaders/`, one per Godot shader in scope:
  - `level_ground`, which includes `headlight_cone` and the water;
  - `level_tree`, which includes `wind_sway`;
  - `level_prop`, which includes `level_prop.gdshaderinc`, for the buildings;
  - `ps1_models_lit` and `ps1_wheel_tire` for the car;
  - `car_shadow`;
  - `ps1_post_process`;
  - the panorama sky;
  - ground cover (the shader `ground_cover.gd` builds inline);
  - `cull`.

  Out of scope: `billboard_particle`, `dust_puff`, `speed_lines`, `car_lamp`, `level_minimap`, `level_tree_id`,
  `log_pile`.
- **Every built-in behaviour from "What Godot draws that we don't write" is written into these shaders:**
  per-vertex lighting (`force_vertex_shading`), fog, nearest filtering with mipmaps, and the LOD rule
  `mesh_lod/lod_change/threshold_pixels=4.0` using the `edge_length` in each scene's `lods`. The
  `[shader_globals]` values come from `shader_globals.json`.
- **Validated without a GPU:** a `cargo test -p render` test parses and validates every `.wgsl` with `naga`. It is
  cheap, runs on every job, and catches most shader mistakes before any adapter is involved.
- **Culling has an exact CPU twin.** `render::cull_cpu(records, camera) -> Vec<u32>` (per-batch visible counts)
  implements the same test as `cull.wgsl`. A GPU test reads the GPU counts back a frame late (the spec's
  per-batch breakdown) and requires exact equality at pinned camera samples. That is a correctness check on
  lavapipe that involves no pixels.

### The benchmark report (3.4)

`app::perf` writes the same JSON shape as `BenchmarkReport.build` (`scripts/benchmark_report.gd`):
- `stats` with `busy_avg_ms` / `_p95` / `_p99` / `_max` and `draw_phase_*`;
- `frames` with `frame_ms`, `busy_ms`, `draw_phase_ms` and `t_s`;
- `device` with `os`, `model` and `web`;
- `label: "rust-viewer-<recording>"`, `timestamp`;
- `draw_breakdown`, which is per batch, from the readback.

The measurements:
- **`busy_ms`:** from the start of the frame callback (`requestAnimationFrame` on web, winit's
  `RedrawRequested` natively) to just after `queue.submit`. This is the same span as Godot's (first step to
  `frame_post_draw`).
- **`draw_phase_ms`:** from the start of encoding to `submit`.
- **`frame_ms`:** a wall-clock delta, never a smoothed one (`features/benchmark.md`, "Two measurement traps").

On web the report goes as `POST /bench` to the page's origin, so `tools/bench_collector.py` stores it unchanged.
Natively it is written to a file. `tools/device_targets.py` then shows Godot and Rust rows side by side. Its
`device_class` and `variant` already key off `device` and `label`.

### The web harness (used by the spike and by 3.3)

- `web/viewer/index.html` loads `build/viewer/viewer.js` and the `.wasm`.
- `tools/build_viewer_web.sh` does the nightly `cargo build` with build-std, then `wasm-bindgen --target web`,
  writing to `build/viewer/`.
- It is served by `tools/bench_collector.py build/viewer <port> build/bench-results`, which already sends
  COOP/COEP. Plain HTTP on localhost counts as a secure context, so no certificate is needed.
- `tools/web_check.mjs` uses Playwright, installed in CI with `npx -y playwright@<pinned> install chromium`. It is
  not added to `tools/package.json`. It launches headless Chromium with
  `--enable-unsafe-webgpu --use-webgpu-adapter=swiftshader --enable-features=Vulkan`, opens
  `?check=<name>`, waits for `window.__check = {ok, detail}`, and exits non-zero on `ok: false` or after a 120 s
  timeout.

## 2. Risks first: the cheapest experiment per risk

Each experiment is a CI job with a pass/fail result the job computes itself. They run before any viewer work, and
Wave C doesn't start until R1–R4 pass. If one fails after two real fix attempts, escalate to Opus with the log. If
Opus can't fix it either, take the fallback, or stop and ask the user where the fallback is a product decision.

## 3. Work packages

Waves own disjoint files. Hand every agent the shared names: `physics::sys::*` (the shim API above),
`render::Probe`, `render::cull_cpu`, `platform::{Window, Workers, load}`, `app::perf::Report`, the `?check=` names
(`jolt`, `jolt_worker`, `gpu`), and `window.__check`.

### Wave A: spike and Godot-side exports (parallel)

#### WP1 — Jolt shim, native (R1, R1b; 3.2)
- **Files:** `.gitmodules` and `third_party/JoltPhysics` (submodule at `036ea7b`); `crates/physics/**`; root
  `Cargo.toml` (adds the member; WP1 owns this file in Wave A and adds `render`, `platform` and `app` as members
  too, so nobody else edits it).
- **Approach:** §1, "Physics". The R1 scene goes in `crates/physics/src/spike.rs` as
  `drop_box_trace(ticks) -> Vec<[u8; 32]>`, so WP4 can call the same function from wasm. Put a one-line comment
  in `build.rs` naming Godot's exclusion list and the commit.
- **Tests:** in `cargo test -p physics`: the rest criterion; two runs give equal traces; a test behind the
  `deterministic` feature on and off that prints the difference (R1b). No tuning values: the numbers come from
  the box's own size.

#### WP2 — `render` skeleton and the GPU probe (R5-compile, R6)
- **Files:** `crates/render/**` (`lib.rs`, `gpu.rs` (the device with default limits), `probe.rs`, `cull.rs`
  (`cull_cpu`), `shaders/cull.wgsl`, `shaders/probe.wgsl`, `tests/wgsl_valid.rs`, `tests/probe.rs`).
- **Approach:** `Probe::run(&Device, &Queue) -> ProbeResult { counts, lit_pixels }`. It is async, polled natively
  with `pollster` (a dev dependency) and awaited on web. The instance records and camera are synthetic: a grid of
  1,000 unit cubes and a camera that sees a known part of it, in three batches.
- **Tests:** `wgsl_valid.rs` (naga, no GPU). `probe.rs` runs only when the env var `TAPPA_GPU=1` is set, so
  `cargo test` on a machine with no adapter isn't red. It asserts that the counts equal `cull_cpu`, and that
  `lit_pixels` is greater than 0 and equals a count worked out from the CPU visible set's projected footprint.
  If the exact footprint is fragile, drop it and keep the counts.

- **Jobs:**
  - **`rust-native`** (ubuntu): `apt-get install mesa-vulkan-drivers`; `cargo test --workspace` with

  - **`rust-web`** (ubuntu): the nightly toolchain from §6, question 2 (`rustup toolchain install` plus
    `rust-src`), `wasi_sdk.sh`, pinned `wasm-bindgen-cli` and `wasm-tools`, then `tools/build_viewer_web.sh`, the

  - **`rust-apple`** (macos-15): the R7 builds and the macOS probe.
  - **`rust-android`:** `cargo install --locked cargo-ndk@<pin>` with the runner's NDK; R7.

#### WP4 — `platform` and `app` minimum, the web harness (R2–R5 runtime)
- **Files:** `crates/platform/**`, `crates/app/**` (`src/main.rs`, `src/web.rs` with `#[wasm_bindgen]` exports
  `run_jolt_trace`, `run_jolt_worker`, `run_gpu_probe`, `src/checks.rs`), `web/viewer/index.html`,
  `tools/build_viewer_web.sh`, `tools/web_check.mjs`.
- **Approach:** the checks call WP1's `drop_box_trace` and WP2's `Probe`. That's why WP4 is in Wave A but
  written against the names above. If WP1 or WP2 changes a signature, they tell WP4 (SendMessage). Native `app`
  has `viewer --check=<name>`, which prints the same `{ok, detail}`, so the R3 comparison is a `diff` of two
  outputs.
- Use the worker crate chosen in §6, question 3.

#### WP5 — Camera path and per-sample live sets from Godot (input for 3.1)
- **Files:** `tools/neutral_geometry.gd`; new `tools/neutral_camera.gd` (`class_name NeutralCamera`);
  `tools/neutral_export.gd` (`--camera=<dir>`); `tools/neutral_check.sh` (one more `export_run`);
  `crates/assets/src/{geometry.rs, camera.rs, lib.rs}` and `bin/asset_check.rs`; `features/neutral-format.md`;
  `tests/headless/test_neutral_assets.gd` (or a new `test_neutral_camera.gd`).
- **Approach:**
  - **Live sets:** in `NeutralGeometry.export`'s 50 m loop, after `prefill_async()`, record the streamer's live
    chunk keys and cover keys. Add a header field `samples: [{pos: [x, y, z], chunks: [i…], cover: [i…]}]`, where
    the indices point into the file's own `chunks` / `cover` lists. So that the indices resolve, keep every
    `(level, coord, mask)` variant that was live, not only the last build of each coord (today `chunks` is
    keyed on `level,x,z` and keeps the last arrays). Key on `level,x,z,mask` instead. Print the size change. If
    the file grows over 2×, keep only variants that are actually referenced.
  - **Camera path:** `NeutralCamera.export(dir)` boots the world the same way (golden mode, the fixture
    profile, `Benchmark.golden`), replays `hafren.rec` with poses written as `LevelReplay._play_tick` does, and
    each tick stores the active `Camera3D`'s global transform (12 floats), `fov`, `near`, `far` and the car's
    transform. It writes `camera_path.tapn` with sections `camera` (f32 × 15 per tick) and `car` (f32 × 12 per
    tick), and a header with `hz`, `ticks`, `logical_size` (`DisplayStretch.logical_size()`) and
    `horizontal_stretch`. The simplest way to drive it is to run `benchmark/level_replay.tscn` with a new
    `--camera-out=<file>` flag that `_physics_process` writes to, rather than copying the replay loop. **Pick
    that** if `level_replay.gd`'s ownership allows it (it is shared golden code, so its existing goldens must
    stay byte-identical).
  - **Rust:** `camera.rs` reads it and adds manifest lines. `geometry.rs` reads `samples`. Godot and Rust
    manifests must still match (the existing `neutral` job checks this).
- **Tests:** a GUT bare-logic test that the sample indices are within range for a tiny synthetic geometry dict
  (call `_write` directly). A Rust unit test that a hand-built camera container reads back.

#### WP6 — Attribute the streaming spike (3.6, first bullet)
- **Files:** `scripts/level_streamer.gd` (`PerfLog.track` keys around `_upload`'s `ArrayMesh.new()` and
  `add_surface_from_arrays`, the `add_child(mi)` at `_upload`'s end, `_restitch`'s mesh rebuild, and the
  `HeightMapShape3D` build plus `body.add_child(cs)` / `add_child(body)` in the collision path);
  `scripts/ground_cover.gd` (the same for the `MultiMesh` build); `features/level-streamer.md` and

- **Approach:** the new keys are `stream_mesh`, `stream_node`, `stream_shape` and `cover_mesh`. They show up in

#### WP7 — Jersey 10 36 px equals 2× of 18 px (3.6, second bullet)
- **Files:** `crates/assets/src/font.rs` (a function `scale_check(&Font) -> Vec<String>` listing the glyphs that
  differ) and `crates/assets/src/bin/asset_check.rs` (`--font-scale` mode); `tools/neutral_check.sh` (runs it and
  prints the result).
- **Approach:** for each glyph from U+0020 to U+00FF, cut the glyph's 18 px bitmap out of `atlas.18.<i>` using its
  UV rect, scale it 2× with nearest-neighbour, and compare it with the 36 px bitmap (and the advance × 2). The data
  is already in `fonts/Jersey10.ttf.tapn`.
- It is a **report, not a gate:** if glyphs differ, the UI section's plan (one 18 px atlas scaled) has to change
  to two atlases. That's a one-line decision for the user, and the plan has room for either.
- WP5 also edits `asset_check.rs`. **WP7 waits for WP5's edit, or they agree by message.**

## 6. Open decisions (recommended default in bold)

1. Jolt binding: **our own `cc`-built shim over a `036ea7b` submodule**, against forking JoltC or `oxijolt-sys`.
   It is the smallest surface, uses the exact commit, needs no bindgen or libclang, and the same build works for
   wasm.
2. Nightly for wasm: **a dated nightly pinned in the workflow and in `tools/build_viewer_web.sh`**
   (the newest one at least two weeks old when WP3 is written), used only for the wasm build, with
   `rust-toolchain.toml` staying on 1.91.0. The alternative, moving the whole workspace to nightly, would make
   every native job less stable.
3. Web workers: **`wasm-bindgen-rayon`**, against `wasm_thread`. It is maintained and widely used, and a pool is
   what streaming needs. Use `wasm_thread` only if rayon's pool can't take the channel-style jobs.
4. Determinism option: **on everywhere in Rust** (`deterministic` default feature), as the spec says, with R1b's
   number handed to Phase 4.
5. GPU on CI: **lavapipe (Vulkan) and WARP (DX12) for correctness, SwiftShader in headless Chrome for WebGPU**,
   with Metal attempted on macOS. Pixel goldens wait until after the user's visual sign-off (spec, "Testing").
6. Textures in the viewer: **RGBA8 from `pixels` everywhere in Phase 3.** Block formats (`blocks.s3tc` /
   `blocks.etc2`) are a per-platform optimisation that doesn't change main-thread time, so they wait until Phase 5.
7. Android packaging: **NativeActivity with `cargo-apk2`** (the smallest moving part). Use `xbuild` only if that
   fails on the current NDK.
8. Terrain chunk choice: **Godot's live sets per 50 m sample** (WP5), not a ported planner. The planner is
   Phase 4's `terrain` crate.
9. Viewer to Pages: **yes, under `/viewer/`** of the existing site. It needs no new hosting, and it is the only way
   the user can test every browser in minutes.
